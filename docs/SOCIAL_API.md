# Social API v1

Local backend: Firebase Standard Firestore, Auth, RTDB and Functions emulators, project `demo-mihon-together`, Functions region `us-central1`. No cloud project is required. Callable JSON times are integer UTC milliseconds; Firestore dates are `Timestamp`. All callables require Firebase Auth and derive the actor from the verified token. Client input never supplies the actor UID.

## Bounds and types

Unknown fields are rejected. UID: 1–128 characters; display name: 1–40; handle: lowercase `[a-z0-9_]{3,24}`; keys: 64 lowercase hexadecimal characters; title: 1–200; source key: 1–160; chapter label: 1–100; page count: 1–2000; page index: 0-based and below page count. Mutation `operationId` is a UUID. A room `sessionId` is a device/session UUID and an operation fence; host UID and live friendship remain mandatory authority.

`Profile = {schemaVersion:1, uid, handle, displayName, createdAt, updatedAt}`.

`SharingSettings = {schemaVersion:1, generation, library, favorites, activity, presence, lastSeen, feed, invisible, updatedAt}`. `feed` was added 2026-10-02; settings written before then lack it, and absent means private everywhere (callables, `socialGetFriend`, Android parsing; rules deny because the field lookup fails). Visibility values are `private|friends`, all default private; invisible defaults false. Every change increments generation. Older projections become unreadable and must be intentionally republished.

`Content = {contentKey,title,sourceKey,sourceWorkKey,editionKey,canonicalProvider:null|anilist|mal|kitsu|mangaupdates,canonicalId:null|string}`. Content/work/edition keys are locally computed SHA-256 identifiers. No images, source credentials, authenticated URLs, local IDs or private notes are uploaded. A canonical work match does not imply an edition/page match.

`SharedEntry = {schemaVersion:1,content,generation,updatedAt}`. Library and social favorites are separate collections; sharing does not reinterpret Mihon's library membership. The first implementation omits progress from shared-library entries.

`Activity = {schemaVersion:1,content,chapterKey,chapterLabel,generation,updatedAt,expiresAt}`; expiry is server-assigned now+120 seconds. A null activity deletes it.

`FeedItem = {schemaVersion:1,kind:chapter_read|favorite_added,content,chapterLabel:null|string,generation,createdAt,expiresAt}` at `feeds/{uid}/items/{slot}`, slot `00`–`49`: a per-user ring buffer (server-only cursor `feedState/{uid}`), so at most 50 items exist and the oldest is overwritten. Expiry is server-assigned now+7 days. `chapterLabel` is required for `chapter_read` and must be null for `favorite_added`.

`Position = {chapterKey,chapterLabel,pageIndex,pageCount,pageMappingKey,stripPosition?}`. Page mapping is explicit and source/edition-specific. `stripPosition` (optional number, `0 ≤ x < pageCount`) is set in long-strip mode: pages from the chapter start to the top of the host's screen (9.37 = 37% into page 10), quantized to 1/200 page. A long-strip follower extrapolates the host's scroll speed and glides toward it every frame (`StripFollower`); other viewers use `pageIndex`. The host writes at most one position per 500 ms with a plain update (the rules enforce lease, session and next sequence), so each update costs one write plus the rules' lookups, not a transaction.

`Room = {schemaVersion:1,hostUid,guestUid,participants:[hostUid,guestUid],content,state:invited|active|closed,epoch,sequence,position:null|Position,writerSessionId:null|string,createdAt,updatedAt,leaseExpiresAt}`. Owner-private `roomLeases/{roomId} = {schemaVersion:1,hostUid,sessionId,epoch}` binds the host device.

| `socialRoomAction` | `{operationId,action:create|invite|join|heartbeat|kick|leave|close|open|position,roomId:null|string,otherUid:null|string,sessionId:null|string,content:null|Content,position:null|Position|{chapterKey,pageIndex},open?:boolean}` (see Group rooms and Open rooms below) | `{room:Room,roomId:string}` |

Mutations store a bounded idempotency result by actor/operation UUID. Reusing a UUID with different input is rejected. Auth registration, sign-in, verification/recovery and logout use Firebase Auth directly; profiles exclude email.

Request ID is SHA-256 of JSON-encoded sorted UIDs. Acceptance is recipient-only and writes both edges atomically. Cancellation is sender-only; rejection recipient-only. Remove/block delete reciprocal edges and pending requests. Unblock never restores friendship. Handle lookup is exact, rate-limited and requires Auth.

`FriendRequest={schemaVersion:1,senderUid,recipientUid,senderHandle,senderDisplayName,recipientHandle,recipientDisplayName,state:pending|accepted|rejected|cancelled|blocked|removed,createdAt,updatedAt}`. Functions copy bounded handle/name fields from validated profiles at request creation so a pending participant can identify the request without broad profile access. No email is included; only the two request participants may read it.

Projection publication accepts at most **50 entries plus deletions combined per request** and never truncates. Android submits as many separate online pages as its library needs; every page has a new operation UUID and the same current generation. Privacy changes cancel the application outbox. There are no Firestore client projection writes or automatic offline retries. Settings changes (including hiding a title) increment generation; functions recheck it transactionally so in-flight stale pages cannot republish. Hidden-title markers prevent future republishing until the owner calls `socialUnhideTitle {operationId, contentKey}` → `{contentKey, restored:boolean}`, which deletes only the caller's marker without bumping the generation or republishing anything.

Room create requires accepted friendship and explicit invitation/content consent, bounded to 20 new invitations per actor per hour. Guest joins; either participant may close/leave, ending v1. Host heartbeats every 30 seconds assign now+90-second expiry and require its bound session. Every room operation returning a full room rechecks reciprocal edges, both block directions, state, epoch and unexpired lease. After revocation/expiry the client terminates locally; cleanup may run separately without returning protected content. Expiration is authoritative even before cleanup.

## Direct reads and host position transaction

Owner-only: accounts, sharingSettings, hiddenTitles, blocks, roomLeases, operations and friendship edges. Server-only: handle index and rate limits. Profiles are owner/accepted-friend readable, with bounded exact discovery through the callable. Requests are sender/recipient readable. Rooms require membership, live accepted friendship and no blocks.

Friend-facing collections: `sharedLibraries/{uid}/entries/{contentKey}`, `sharedFavorites/{uid}/entries/{contentKey}`, `activities/{uid}`, `presence/{uid}`, `lastSeen/{uid}`. Rules consult current sharing settings plus reciprocal friendship and blocks. Each metadata projection must match current generation. Existing activity reads also require an unexpired server expiry. An absent activity document is readable only to its owner or a currently accepted friend with activity consent, so a listener can observe missing → published → cleared → republished activity within one generation. Expired activity still denies reads; clients expire received data locally and recover via a fresh read or listener.

Library query: `whereEqualTo("generation", sharing.generation).orderBy(documentId()).limit(50).startAfter(lastId)`. Fetch generation/visibility via `socialGetFriend` before querying. Continue until the page is shorter than the limit. Request queries use `senderUid` or `recipientUid` plus `state=pending` and limit 50. Accepted edge reads use the owner's subcollection. Subscribe to a known room ID; no broad room list.

Owner-only `roomInvites/{uid}/items/{roomId}={schemaVersion:1,roomId,state:invited|active|closed,updatedAt}` discovers sessions without revealing content. Both participants' indexes update on create/join/close. Query `whereIn("state",["invited","active"]).orderBy("updatedAt",descending=true).limit(50)`. The room's current ACL and expiry remain authority: discard denied/expired references from the displayed session list.

Host positions use an **online Firestore transaction**, with one in-flight transaction and one coalesced pending latest position. Read the room and private lease; update only `position`, `sequence=old+1`, `writerSessionId=currentSessionId`, and `updatedAt=serverTimestamp()`. Rules check the full room validator, host identity, unchanged membership/epoch, live ACL, unexpired lease and writerSessionId equality with the private lease. Guests cannot write. Never queue ordinary room writes offline; reconcile failures against a fresh server snapshot. Followers use only authorized server snapshots, wait for explicit chapter/page compatibility, and suppress outgoing echo.

RTDB `connections/{uid}/{connectionId}={connectedAt:ServerValue.TIMESTAMP}` is owner-private. Register and await `onDisconnect().removeValue()` before setting; keep a permitted non-info listener during the foreground session. Presence is derived in Firestore and never grants permission. The bridge rereads current RTDB state inside each retrying Firestore transaction and only advances lastSeen on an all-devices-offline transition. The trigger does not auto-retry (decided 2026-10-02, to avoid billed retries); a failed run leaves the mirror stale until the next connect or disconnect.

`presence/{uid}={schemaVersion:1,state:online|offline,updatedAt}`; `lastSeen/{uid}={schemaVersion:1,lastSeenAt}`. Android derives its online boolean from `state=="online"` and treats stale updates as uncertain. Production callable deployment enforces App Check; a distribution-appropriate Android App Check provider must be configured before production calls can succeed. Emulators bypass enforcement.

## Official APIs and scope

Implementation follows [callable Functions](https://firebase.google.com/docs/functions/callable), [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions), [Android RTDB presence](https://firebase.google.com/docs/database/android/offline-capabilities) and [Firestore presence](https://firebase.google.com/docs/firestore/solutions/presence). Firestore transactions can retry and fail offline. Presence is asynchronous and measures RTDB connectivity.

Emulator/domain tests demonstrate the tested authorization and transition cases; generated Security Rules are a prototype requiring review before broad distribution. Production App Check, complete account deletion, abuse tuning and real-device mapping/presence testing remain release requirements.

## Recent-activity feed (2026-10-02)

`socialPublishFeed` requires the current generation, `feed=friends`, not invisible, and a title that isn't hidden. The same kind/title/chapter repeated within 10 minutes returns `published:false` without writing. Android publishes `chapter_read` the first time a chapter is completed in the reader, and `favorite_added` when a social favorite is ticked. Both are best-effort: failures are logged, never retried, and there is no outbox. Incognito sources are skipped.

Friends read with `whereEqualTo("generation", g).whereGreaterThan("expiresAt", now + 1h).orderBy("expiresAt", desc).limit(20)`. Rules require friendship, `feed` consent, not invisible, `generation == current` and `expiresAt > request.time`. Query rules can only prove the last condition from the query's own bound, so clients use a bound one hour ahead: this tolerates device clock lag, at the cost of hiding an item's final hour. Composite index: `items`(generation asc, expiresAt desc). Expired items stay in storage until overwritten or removed by a production TTL policy on `expiresAt` (Phase 7).

## Room chat and reactions (2026-10-02)

`socialRoomMessage {operationId, roomId, kind:text|reaction, text:null|string, emoji:null|string}` returns `{seq, createdAt}`. Text is 1–200 characters on a single line (no control characters) and is trimmed. A reaction must be one of `👍 😂 😮 😢 😡 ❤️ 🔥 👏`; Android keeps the same list (`RoomMessage.REACTIONS`, drift-checked in a test). The sender must be a participant with live friendship, and the room must be `active` with an unexpired lease. Limits per sender per room: at least 1 s between messages and at most 30 per minute (`resource-exhausted`).

Messages are written to `rooms/{roomId}/messages/{000–099}`, a 100-slot ring with a server-only cursor `roomChat/{roomId}` and server-only rate docs `roomChatRates/{roomId}/users/{uid}`. The first close or leave of a room deletes every slot, the cursor and the rate docs. Clients read with `orderBy("seq", desc).limit(30)`. Android shows the latest 10 messages in the Read together dialog. New messages (never the first, historical snapshot) pop out over the reader: the friend's from the left edge, mine from the right. A floating emote button opens the reaction picker while the room is active.


## Daily quotas and cleanup (2026-10-02)

Every mutation also counts against per-user, per-UTC-day caps (`DAILY_LIMITS`, total `DAILY_TOTAL` = 8,000). Exceeding a cap returns `resource-exhausted` ("Daily limit reached"); idempotent replays don't count. A scheduled `socialCleanup` function closes rooms whose lease expired without a close. See [production readiness](PRODUCTION.md).


## Daily ranking (2026-10-02)

Opt-in `stats` sharing category (private by default; absent means private). `socialRecordChapter {operationId, generation, pages:1..2000}` → `{day, chapters, pages}`. It requires the current generation, `stats=friends` and not invisible, at least 10 s between calls and 300 per day. It increments `dailyStats/{uid}/days/{yyyymmdd}` (UTC day, `expiresAt` 8 days, generation-fenced; a privacy change restarts the day's counter). Friends read single documents for today; rules require friendship, stats consent, the current generation and the owner not being invisible. Android records on the first completion of a chapter (not incognito, not invisible) and shows **Today's ranking** in Friends: chapters, then pages, with 🥇🥈🥉.


## Customizable profiles (2026-10-02)

Profiles gain `bio` (one line, ≤160 characters), `accent` (0–7) and optional `avatar` and `banner`, each `{version, contentType, size}`. The images live in Cloud Storage at `profileMedia/{uid}/avatar|banner`: PNG, JPEG, WebP or GIF (animated GIFs play), at most 2 MB for avatars and 5 MB for banners. The app uploads first, then calls `socialUpdateProfileStyle {operationId, bio, accent, avatar:keep|set|remove, banner:keep|set|remove}`, which checks that the stored object exists with an allowed type and size before referencing it. `socialUpdateProfile` keeps style fields when the handle or name changes. **`socialLookupHandle` now returns only `{schemaVersion, uid, handle, displayName}`**, so bios and media are never exposed to non-friends. Friends see the full profile (profile rules and `socialGetFriend`). Android caches media bytes per version (24 MB LRU) and renders them with a GIF/animated-image decoder.


## Streaks and invite links (2026-10-02)

`socialRecordChapter` now also returns and stores `streak`: consecutive UTC days with at least one chapter. It continues only from yesterday's document in the same consent generation, otherwise it restarts at 1. The ranking shows 🔥 N for streaks of 2 or more.

### Global ranking (2026-10-03)

`sharingSettings.globalRanking` (boolean, **absent means true**: the one switch that starts on, by Berti's decision; the app shows a one-time notice with an opt-out). `socialUpdateSharing` accepts it as an optional extra field in `settings`; leaving it out keeps the current value, so older clients still work.

`socialRecordChapter` now counts when `stats=friends` **or** the user is ranked globally (`globalRanking` not false and not invisible). When ranked, it also upserts `leaderboards/{yyyymmdd}`: `{schemaVersion, day, entries: {uid: {handle, displayName, accent, chapters, streak, updatedAt}}, updatedAt, expiresAt}`, kept to the top 50 (lowest count drops; among ties the latest arrival). Opting out or going invisible removes the entry at once from the all-time board and every daily board still kept (8 days); renaming or a new accent updates it; account deletion removes today's and yesterday's entries. Rules: any signed-in user may read `leaderboards/*`; nobody may write. Pages are never on the board.

Android: Today's ranking has **Friends** and **Global** tabs and shows chapters only. Tapping a friend opens their profile; tapping anyone else opens a public card (name, handle, today's chapters, streak) with **Add friend** (a request by handle). Blocked accounts are hidden from the global tab.

Invite links: `mihontogether://add/<handle>` opens Friends with the handle pre-filled (Android intent filter; only valid handles are accepted, `FriendInvite.parse`). **Share invite link** in Friends shares the handle, the app link and, if `social-web-url` is configured, `<web>/add/<handle>`. The web `/add` page offers both sending the request and opening the app.

### Covers and paged libraries (2026-10-03)

Content objects may include an optional `coverUrl` (https, 9–500 characters, no whitespace or control characters); domain validation and the rules' `validContent` accept it everywhere content appears. Android only fills it in library/favorites projections when the device's "Share covers" switch is on, and only for https thumbnails (never local or custom covers). Friends read a projection A–Z with `where(generation == current).orderBy(content.title)` and cursors (composite index `entries: generation ASC, content.title ASC`) and count it with an aggregate `count()` query.

### Push notifications (2026-10-03)

`socialRegisterDevice {operationId, action: "register"|"unregister", token}` (token 20–4096 chars of `[A-Za-z0-9:_-]`, 50 calls/day) stores `devices/{uid}: {tokens: {id: {token, updatedAt}}}`, newest 10, no client reads. Pushes are FCM **data** messages `{kind, name, handle?, title?, roomId?}` with `kind` in `friend_request | friend_accepted | room_invite | message | join_request`; the phone builds the text and checks its own per-kind switch. Sent after the mutation commits, never for idempotent replays; tokens FCM reports unregistered are removed.

### Private messages (2026-10-03)

`socialMessage {operationId, action: "send"|"read", otherUid, text}` (text required for send: one line, 1–500 chars; null for read; 2,000/day). Requires an accepted, unblocked friendship. Send writes `chats/{pairId}/messages/{seq:10 digits} {seq, senderUid, text, createdAt, expiresAt}`, `chats/{pairId} {participants (sorted), next, updatedAt, expiresAt}` and both `chatIndex/{uid}/chats/{other} {chatId, otherUid, lastText (100), lastSenderUid, unread, updatedAt, expiresAt}`; read zeroes my unread. 30-day TTL. Rules: chats and messages readable by participants while friends; chatIndex owner-only; nothing client-writable. Remove/block deletes both chatIndex entries; account deletion deletes the conversations.

### Group rooms (schema v2, 2026-10-03)

`rooms/{id}`: `{schemaVersion: 2, hostUid, participants: [uid…] (2–6, everyone with access), members: {uid: {state: "joined"|"invited", name, accent, joinedAt, invitedAt}}, maxMembers: 6, content, state, epoch, sequence, position, writerSessionId, createdAt, updatedAt, leaseExpiresAt}`. `socialRoomAction` actions: `create {otherUid, sessionId, content, position?}`, `invite {roomId, otherUid}` (host; friend of the host; room not full; 20/h with create), `join {roomId}`, `heartbeat {roomId, sessionId}` (host lease; claims a lease whose `sessionId` is null after a hand-off; prunes members without an accepted edge from the host; closes when the host is alone), `kick {roomId, otherUid}` (host), `leave {roomId}` (member: removed, closes if the host is alone; host with a live lease: hand-off to the earliest-joined member, epoch + 1, lease `{hostUid: new, sessionId: null}`, non-friends of the new host removed; host after expiry or with nobody joined: close), `close {roomId}` (host: close; member: leave). Removed people's `roomInvites` entry turns `closed`. Room chat gains server-written lines with `kind` `joined | left | removed | host` (about `senderUid`); `socialRoomMessage` needs a joined member who is the host's friend. Rules: `activeRoom` = participant, open, leased, and host or host's friend; host position writes unchanged.

### Ask to read along (2026-10-03)

`socialJoinRequest {operationId, action: "ask"|"decline", otherUid}` (200/day). `ask` requires an accepted friendship and that the friend shares `activity`, isn't invisible and has an unexpired `activities` doc; it writes `joinRequests/{friend}/items/{me} {requesterUid, name, handle, createdAt, expiresAt (+10 min)}` once per pending pair (10 per hour) and pushes `join_request`. `decline` (by the friend, `otherUid` = requester) deletes it; room `create`/`invite` of the requester deletes it too, as do remove/block and account deletion. Rules: owner-only reads.

### Room source (2026-10-03)

Content objects may carry `source: {id: "<numeric source ID>", name (1–80), lang (1–12), pkg (extension package or null)}`; validated in `validateContent` and the rules' `validContent`. Android sets it only on room `create`, so friends can be guided to the extension (installed → search the title in it, available in their stores → install, untrusted → trust, otherwise name it).


### XP and levels (2026-10-03)

`socialRecordChapter` accepts an optional `roomId` (64-hex) besides `{operationId, generation, pages}`. It now succeeds whenever the generation matches and the account isn't invisible: daily stats and the ranking are written only under consent as before (`counted: false` otherwise), and XP is always counted into `xp/{uid} {total, level, day, today, chapters, together, streak, bestStreak, createdAt, updatedAt}`. Per chapter: 10 XP, +5 when `roomId` names an active, leased room where I and at least one other member have joined, and on the day's first chapter +5 × the XP streak (consecutive UTC days, max 7 days counted). At most 1,000 XP a UTC day; same 10 s minimum gap as stats. Level L needs `25·L·(L−1)` XP (L2 = 50, L3 = 150, L5 = 500, L10 = 2,250). The reply adds `xp: {gained, total, level, leveledUp}`. Global ranking entries gain `level`. Rules: `xp/{uid}` readable by the owner, and by friends while `stats == "friends"` and not invisible; never client-writable. The Android client calls it for every finished chapter outside incognito and invisible mode.

### Group chats (2026-10-03)

`socialGroupChat {operationId, action, groupId, name, uids, text}` (unused fields null; 2,000/day). Actions: `create {name (1–40, one line), uids (1–19 friends)}` (10 a day; the group ID is derived from the creator and operation ID), `add {groupId, uids}` (my friends, up to 20 members), `remove {groupId, uids: [one]}` (owner only), `leave {groupId}` (an owner leaving passes ownership to the longest member; the last member out deletes the group), `rename {groupId, name}`, `send {groupId, text (1–500, one line)}` (1 s gap and 30 a minute per member), `read {groupId}`. Writes `groups/{groupId} {groupId, name, ownerUid, members (join order), names: {uid: {name, handle, accent, since, joinedAt}}, next, createdAt, updatedAt}`, `groups/{groupId}/messages/{seq:10} {seq, kind: "text"|"event", senderUid, senderName, text, event?: created|added|removed|left|owner|renamed, createdAt, expiresAt (+30 days)}` and every member's `groupIndex/{uid}/groups/{groupId} {groupId, name, members, lastText, lastSenderName, unread, updatedAt}`. Pushes `group_added {name, title: group name, groupId}` and `group_message {name, title: text, group, groupId}`. Rules: the group document is readable by current members; messages by current members with `seq >= names[me].since` (queries must include `where seq >= since`); `groupIndex` owner-only; nothing client-writable. Unfriending doesn't remove anyone from a group. Account deletion removes the member from each group (ownership passes on).

### Achievements, weekly XP and streak freezes (2026-10-03, later)

All inside `awardXp` (no extra reads). `xp/{uid}` gains `badges: {id: unlockedAt}` (`BADGES` in `domain.ts`: chapters 1/50/250/1000, together 1/25/100, best streak 3/7/30/100, 20 chapters in a UTC day, 30 reading days, level 10/25), `days`, `dayChapters`, `bestDay`, `week` (UTC Monday, yyyymmdd), `weekXp`, `lastWeekXp` and `freezes` (0–2: one earned each time the XP streak reaches a multiple of 7; each covers one missed day). The `xp` reply adds `unlocked: [ids]` (new only) and `freezeUsed`. The friends "This week" ranking reads friends' `xp` docs (same rule as before) and treats a stale `week` as 0.

### Group chat hardening (2026-10-03, later)

`create`/`add` refuse anyone who has a block, in either direction, with a current member or another new member (`permission-denied`). `send` skips pushes between people with a block. The apps hide messages from people I blocked. `groupIndex` entries carry `previewExpiresAt` (+30 days from the previewed message). The scheduled `socialCleanup` blanks expired previews (`clearExpiredGroupPreviews`; single-field collection-group index on `groups.previewExpiresAt`). Account deletion writes "left" and "owner" lines and updates the remaining members' counts.

### Ready check in rooms (2026-10-03, later)

`socialRoomMessage` accepts `kind: "ready" | "wait"` with `text: null, emoji: null`. The server stores a fallback `text` ("✅ Ready for the next chapter" / "⏸ Wait for me") so older apps show it as a chat line. Clients take each member's latest signal sent after the host's last chapter change, within 15 minutes (`RoomSignals`). The app shows ✅ / ⏸ in the member list, counts in the emote picker, and a popup when someone signals.

### Recommend a title (2026-10-03, later)

`socialMessage` (`send`) and `socialGroupChat` (`send`) accept an optional `content` (validated like shared entries, including an optional `coverUrl` and `source`). With `content`, `text` may be null (stored as ""). The message document gets `content`; list previews and pushes read "📖 {title}" (" · {text}" when there is text). Other actions reject `content`. The apps show a title card (cover, name, source); tapping it opens the title in my library or searches for it. The 📖 button next to the message box picks one of my library titles; its public cover link is included when "Share covers" is on.

### Cover thumbnails and tracked IDs (2026-10-03)

Many sources refuse to show their covers on other websites, so the web had blank tiles. When sharing the library with "Share covers" on, the phone uploads a 240 px JPEG (at most 90 KB; the rules allow 100 KB) of each shared title's cached cover to Storage `coverThumbs/{uid}/{contentKey}`. These are only titles friends can see: everything when the library is shared, otherwise favorites. Shared content gains `thumb: true` (validated as true-only in `validateContent` and `validContent`). Storage rules: the owner writes `image/jpeg|webp` to 64-hex keys; reads are open to the owner, and to friends while the owner shares library or favorites. Uploads are skipped when already done for the same cover link. Thumbnails of titles no longer shared, and all of them when "Share covers" is turned off, are deleted. Account deletion removes the prefix. Tracked titles also carry `canonicalProvider`/`canonicalId` from Mihon's AniList (tracker 2) or MyAnimeList (tracker 1) entry, but never the tracking progress. The web tries, in order: the source's cover, the thumbnail, AniList by ID (`Page { media(id|idMal) }`), and AniList by title.

### Push routing uid (2026-10-03, later)

Every push that points at a person now carries that person's uid as `uid` (string) in the FCM data, next to the existing fields: `message` (sender), `group_message` (sender; `groupId` as before), `group_added` (the member who added me), `friend_request` (requester), `friend_accepted` (accepter), `join_request` (requester), `room_invite` (host; `roomId` always present, on `create` and `invite`). New kind `read_match {name, title, uid}` (see Read matches). No existing field was removed or renamed.

### Room source URL (2026-10-03, later)

`content.source` may carry an optional `url`: the host's manga URL as the extension knows it (`SManga.url`), 1–500 characters, no whitespace or control characters, starting with `/` or `https://` (non-empty after the scheme). Validated in `validateSource` (domain) and in the rules' `validContent` (`source.keys().hasOnly(['id','name','lang','pkg','url'])`, same bounds and pattern). Room members can read it like the rest of the room content. Only rooms use `source`; Android never puts it into library entries.

### Read matches, "Let's read this" (2026-10-03, later)

`socialReadWish {operationId, action: "add"|"remove", otherUid, content}` (content validated like shared entries; `remove` sends the same content object; 100 calls/day on top of the limits below). Returns `{state: "wished"|"matched"|"removed"}`.

- `add` requires an accepted, unblocked friendship and `otherUid` ≠ me (`permission-denied` / `invalid-argument`). At most 50 new wishes per actor per UTC day (`readWishLimits/{uid} {day, count}`, server-only; re-adding an existing wish is a no-op returning the current state and isn't counted).
- Storage (server-only): `readWishes/{pairId(a,b)}/items/{contentKey} {schemaVersion, contentKey, content, flags: {uid: addedAtMs}, createdAt, updatedAt, expiresAt (+60 days)}`. Each person's own list: `readWishIndex/{uid}/items/{otherUid}_{contentKey} {schemaVersion, otherUid, contentKey, content, matched: bool, matchedAt: ms|null, createdAt, expiresAt (+60 days)}`. Both are in collection group `items`, whose `expiresAt` TTL deletes them.
- When the other person's flag already exists, it's a **match**: both index entries get `matched: true, matchedAt`; a line is appended to the pair's private chat (`chats/{pairId}/messages/{seq}` `{seq, senderUid: actor, text: "", content, system: "match", createdAt, expiresAt (+30 days)}`, plus `chats/{pairId}` and both `chatIndex` entries with `lastText` "🤝 You both want to read {title}", unread +1 for the other person only), and the other person gets the push `read_match {name: my display name, title, uid: me}`. A one-sided wish is never revealed: no push, no document the other person can read.
- `remove` deletes my flag (the pair document when no flag remains) and my index entry; if it had matched, the other person's entry becomes `matched: false, matchedAt: null` (their flag stays). `remove` does **not** require the friendship, so a former friend can still clean up their own list.
- Rules: `readWishIndex/{uid}/items/{id}` readable by the owner only; `readWishes/**` and `readWishLimits/*` have no client access; nothing is client-writable.
- Account deletion: for each of my `readWishIndex` entries it deletes `readWishes/{pairId(me, otherUid)}/items/{contentKey}` and the other person's entry `readWishIndex/{otherUid}/items/{me}_{contentKey}`, then my `readWishIndex` tree and `readWishLimits` doc.

### Room recap line (2026-10-03, later)

Rooms store `startChapterLabel` (the `create` position's `chapterLabel`, or null) — server-written, allowed by the rules' `validRoom` key set (optional, null or 1–100 chars) and not in the host-writable position diff. Older rooms without it keep working.

When a room closes through any path (host `close`, a `leave` that closes it, the heartbeat closing it, `expireRoom` cleanup) — or the host leaves and the hand-off leaves the successor alone — and exactly two people had joined (host + one guest: members with a `joinedAt`), the session lasted at least 5 minutes (from the later `joinedAt` to `min(close time, leaseExpiresAt)`), and both are still accepted, unblocked friends, a system line goes into their private chat: `chats/{pairId}/messages/{seq} {seq, senderUid: hostUid, text: "", system: "recap", recap: {title, fromChapter: startChapterLabel|null, toChapter: last position chapterLabel|null, minutes}, createdAt, expiresAt (+30 days)}`. Both `chatIndex` entries get `lastText` "📖 Read together: {title}" and `lastSenderUid` = host, **without** changing unread counts. No push. Rooms where 3 or more people were joined at close get no recap (v1).

Private chat messages can therefore carry `system: "match" | "recap"` (absent for normal messages); apps that don't know a value should show `content` (match) or nothing special.

### Replies and reactions in chats (2026-10-06)

Both `socialMessage` and `socialGroupChat` gain three optional input fields. Older apps leave them out; absent and null mean the same.

- **Reply:** `send` may carry `replyTo` (the replied message's `seq`, integer ≥ 0). The server reads that message and stores a quote on the new one: `replyTo: {seq, senderUid, preview}` (groups add `senderName`). `preview` is the first 100 characters (code points) of the original text, or "📖 {title}" for a recommendation. The original must exist, not have expired (`expiresAt > now`), be a regular message (no private `system` line, no group `event`) and, in a group, be one I can read (`seq >= names[me].since`); otherwise the send fails with `invalid-argument` (no quote-less fallback, so the app can tell the person). The chat list preview, unread counts and the push are the same as for any message (the quote isn't in them). Other actions reject a non-null `replyTo`.
- **React:** new action `react` with `seq` and `emoji` (and `text: null`, no `content`/`replyTo`): `socialMessage {operationId, action: "react", otherUid, text: null, seq, emoji}`, `socialGroupChat {operationId, action: "react", groupId, name: null, uids: null, text: null, seq, emoji}`. One reaction per person per message, stored on the message as `reactions: {uid: emoji}` (the field is removed when empty): a new emoji replaces mine, the same emoji again removes it. Returns `{chatId | groupId, seq, emoji}` with my reaction afterwards (`null` when removed). The target follows the same rules as a reply target. Private chats need an accepted, unblocked friendship; groups need membership. Reacting changes nothing else: no unread count, no chat list preview, no push, the message's `expiresAt` stays. Other actions reject non-null `seq`/`emoji`.
- **Emoji validation** (server `isReactionEmoji`, mirrored by the app's `ReactionEmoji` and the web's `isReactionEmoji`; Berti's decision: any emoji is allowed): at most 16 UTF-8 bytes and exactly one emoji — an `Extended_Pictographic` code point with an optional U+FE0F and skin tone (U+1F3FB–1F3FF), ZWJ sequences of those, a keycap (`[#*0-9]` U+FE0F? U+20E3) or a flag (two regional indicators). Letters, digits on their own, whitespace, control characters and several emojis are rejected (`invalid-argument`). Long ZWJ families (over 16 bytes) and subdivision flags don't fit.
- **Limits:** reactions don't count against the message quotas. They have their own daily quota (`quotas/{uid}.counts.socialReaction`, 2,000 a day, still inside the 8,000 daily total) and a burst limit of 60 a minute per person across all chats (`reactionLimits/{uid} {count, windowStartedAt}`, server-only, deleted with the account). Idempotency is unchanged (`operationId`; a replayed `react` doesn't toggle twice).
- **Rules:** unchanged — clients read messages directly (the new fields ride along), nothing is client-writable. Account deletion deletes private conversations as before; in groups, a deleted user's reactions (uid keys) stay on other people's messages until those expire, like their old messages' display names.
- **Apps:** long-press a message for the reaction bar (❤️ 😂 😮 😢 😡 👍 and "+" for any emoji), Reply and Copy; swipe right to reply; a reply bar above the input; quotes inside the bubble (tap to jump to the original when it's loaded); reaction chips with counts under the bubble (mine highlighted; tapping a chip toggles my reaction to that emoji). The web has a Reply / React action per message and the same chips and quotes.

### Friends who read this, ratings and reviews (2026-10-06)

**Reading progress.** A `socialPublishEntries` entry of kind `library` may carry `progress: {read, total, finished}` next to its content fields (integers 0–100,000, `read ≤ total`, `finished` only when `total > 0 && read == total`). It is stored beside the projection: `sharedLibraries/{uid}/entries/{contentKey} = {schemaVersion, content, progress?, generation, updatedAt}`. Favorites reject it; entries without it stay valid (older clients). Android sends it only for titles where at least one chapter was opened (Berti's decision: that counts as "read"; `read` may be 0), only while library sharing is on, and diffs against what is published so unchanged entries aren't rewritten. Besides **Publish**, the app refreshes quietly at most every 6 hours, only within the generation it last published in (after a privacy change sharing again stays a deliberate Publish). Friends read started titles with `where(generation == g).where(progress.read >= 0).orderBy(progress.read)` (composite index `entries: generation ASC, progress.read ASC`); the same projection rules apply.

**Title matching (`TitleMatch`, Android).** My title and a friend's are the same work when, in order: (1) same `sourceWorkKey` → same; (2) both carry an ID from the same tracker (AniList, MyAnimeList, Kitsu, MangaUpdates; mine from all my tracks, theirs from `canonicalProvider/Id`) → equal = same, different = different; (3) same source but another entry → different; (4) normalized titles equal (mine: source title plus my trackers' titles) → same. Normalization: NFKC, lowercase, accents removed on Latin letters only, `&` → and, apostrophes dropped, other punctuation and spaces removed; bracket groups made only of edition words (official, colored, webtoon, manhwa, raw, digital, english/kr/jp…) and trailing raw/official/colored/webtoon are dropped. Numbers, seasons, subtitles, format words (novel, anthology, doujinshi) and leading articles are kept; keys shorter than 3 characters never match. A friend's title I don't have is searched in their source when I have it installed (my source IDs hashed like `sourceKey`), otherwise across my sources.

**`workKey`** = SHA-256 hex of `work-v1|canonical|{provider}|{id}` when the content carries a tracker ID, else `work-v1|source|{sourceWorkKey}` (backend `workKey`, Android `TitleMatch.workKey`, shared test vectors).

**`socialReview {operationId, action: "set"|"delete", content, rating, text}`** (60 calls/day). `content` is validated like shared entries but may not carry `source`. `set`: `rating` integer 1–5, `text` null or 1–1,000 characters of plain text (line breaks allowed, at most 30 lines; trimmed, blank = null); hidden titles are refused; at most 30 sets a UTC day (`reviewLimits/{uid}`, server-only). Returns `{workKey, review}`. `delete`: `rating` and `text` null; returns `{workKey, deleted}`. Stored at `reviews/{uid}/items/{workKey} = {schemaVersion, workKey, content, rating, text, createdAt, updatedAt}` (editing keeps `createdAt`). When a title's work key changes (e.g. it got tracked), Android deletes the older review after saving the new one, but only when the older one matched by source entry or tracker ID. Hiding a title deletes its review (see Review fixes below).

**Reviews setting.** `sharingSettings.reviews` (boolean, **absent means on**, Berti's decision). `socialUpdateSharing` accepts it as an optional extra in `settings` like `rankingMedia`; leaving it out keeps the current value. `socialGetFriend` returns `sharing.reviews` (false while the friend is invisible). Turning it off hides reviews at once without deleting them. Rules: `reviews/{uid}/items/*` readable by the owner, and by accepted, unblocked friends while `reviews != false` and the owner isn't invisible; never client-writable. Friends read `orderBy(updatedAt, desc).limit(100)`. Account deletion removes `reviews/{uid}` and `reviewLimits/{uid}`. No "rated" feed item yet: older Android builds would show an unknown feed kind as "added to favorites".

**Apps.** Android: on a title page, a Friends row under the description (avatars, "Alex and Shikori1 read this"; tap for each friend's progress, stars and review; tap a friend for their profile) and **Rate** once a chapter was opened (not for incognito sources). Friends' started titles and reviews are loaded once per signed-in session when a title page first needs them, cached for five minutes (see Review fixes below), and dropped at once when an accepted edge goes. Friend profiles get a Reviews section; Me → privacy gets a Reviews switch. Web: progress badges on library covers, friends' reviews on their profile page, the Reviews switch on the privacy page; reviews are written in the app.

### Review fixes (2026-10-06)

- **Hiding a title deletes its reviews.** `socialUpdateSharing` with `hideContentKey` also deletes the actor's `reviews/{uid}/items/*` whose `content.contentKey` equals the hidden key (found with a query inside the same transaction: the `Store`'s `Transaction.query(collection, field, value)`, single-field index, no new composite index). A tracked work reviewed from another source keeps its review (it carries the other title's key).
- **Progress setting.** `sharingSettings.progress` (boolean, **absent means on**), an optional extra in `socialUpdateSharing.settings` like `reviews`; leaving it out keeps the current value (older apps). `socialGetSelf`/`socialGetFriend` return `settings.progress`/`sharing.progress`. While it's off, `socialPublishEntries` stores library entries **without** `progress` even when an (older) app sends it; since every settings change bumps the generation, entries published before are unreadable until republished, and the republish drops progress. Apps: Android Me → privacy "Share reading progress", web privacy page toggle; friends' apps ignore progress while `sharing.progress` is false. Android never computes progress for titles from incognito sources and skips the quiet 6-hour refresh while global incognito is on (Mihon's history doesn't record which reads were incognito). Deploy the backend before shipping an app that sends `progress` in `settings`: older backends reject unknown fields.
- **Ranking pictures** (`storage.rules` `rankingPicture`): besides the settings checks (ranking on, not invisible, `rankingMedia` on), the owner must have an entry on `leaderboards/alltime` (`uid in entries`), and the viewer must not be on the owner's block list (`blocks/{owner}/users/{viewer}`). Friends' access is unchanged.
- **Group quotes from before I joined.** The server can't hide a field per reader, so the apps show a `replyTo` whose `seq` is below my `since` in that group as "Earlier message" (no name, no preview). Quotes and reactions of people I blocked are hidden in groups too (quote shown as "Earlier message"-style placeholder, reactions left out of the chip counts).
- **Friends who read this (Android).** Kept 5 minutes instead of an hour; reloads by itself while a title page is open and when the app comes back to the foreground; a friend's settings seen on their profile drop what they no longer share at once. Known settings are reused for 30 minutes instead of one `socialGetFriend` per friend per load; a denied read asks for the current settings once. Loads run in the cache's own scope. Per friend at most 500 started titles and 100 reviews. Rating a title only replaces my older review of a matching work when it matched by source entry or tracker ID (a title-only match keeps both).


## Nudges (2026-10-06)

`socialNudge {operationId, otherUid}` sends an accepted, unblocked friend a light push; returns `{nudged: true}`. Limits: one nudge per pair per 24 h and 20 different people per UTC day (`resource-exhausted`), plus 60 calls/day. Bookkeeping lives only in the server-only `nudgeLimits/{uid}` (`day`, `count`, `pairs {otherUid: at}`; deleted with the account); no client-readable document is written. Push `kind: "nudge"` with `name` (sender), `uid` (sender) and, only when the target shares stats with friends, is not invisible, has a streak of 2+ and last read yesterday (UTC), `title` = the streak as a string. The app shows "{name} nudged you" with a streak line or "Keep reading today."; tapping opens Friends. The app remembers a sent nudge for 24 h on the phone ("Nudged"), and shows a nudge icon in the friends list when a readable friend's streak is at risk (same rule, from `xp/{uid}`: `streak >= 2`, `day` = yesterday). The web profile has the same button (state in localStorage).

### Invites and recruiter badges (2026-10-06)

- **`socialFriendAction` request** takes an optional `via: "invite" | null` (older clients omit it; any other value, or `via` on another action, is `invalid-argument`). The app and web send `"invite"` when the handle came from that person's invite link, friend code or clipboard. The pending `FriendRequest` then carries `via: "invite"`, unless the pair was ever friends: an accepted request is stamped `everFriends: true`, which later requests between the two keep, and such a pair never counts as an invite.
- **On accept** of an invite request, the server files `invites/{newcomer}` = `{schemaVersion, inviterUid, baseChapters, state: "pending"|"credited"|"dropped", createdAt, updatedAt, creditedAt?}` (newcomer = the sender; inviter = the recipient who accepted). One inviter per account, ever: an existing doc is never replaced. Server-only collection (no rules match, so clients can't read it). When the newcomer already has an `xp` doc it gains `invitePending: true` so `socialRecordChapter` only reads the invite while one may be pending (and for a reader without an xp doc yet).
- **Credit** (`RECRUIT = {chapters: 5, xp: 50, monthlyCap: 10}`): in `socialRecordChapter`, once the newcomer's lifetime `chapters` reach `baseChapters + 5`, the inviter gets `+50` XP and `recruits + 1` on `xp/{inviter}` (`recruitMonth` yyyymm, `recruitMonthCount`, `recruitedAt`), and the invite turns `credited`. The bonus is **outside the daily XP cap and not part of the weekly XP**; it leaves the inviter's `updatedAt` alone (their own 10 s chapter gap is unaffected) and reaches the all-time board on their next counted chapter. If the friendship is gone by then the invite is `dropped`. At 10 credits in the inviter's current UTC month the credit waits and is retried on the newcomer's later chapters (e.g. next month).
- **Badges** `recruit_1`, `recruit_3`, `recruit_10` (field `recruits`) in `BADGES`; app `Badge` and web `BADGES` carry names and icons (📨 🎉 🏰).
- **Friend code** (no install referrer without the Play Store): the web `/add/<handle>` page shows the handle as a friend code with Copy, which copies `mihontogether-invite:<handle>`. Android, signed in with a profile, no friends and no outgoing request, reads the clipboard **once per install** (preference `social_invite_clipboard_checked`) and acts only on that format or a `mihontogether://add/` link; Friends also offers "Got an invite? Enter a friend code" (code, link or plain handle). Either way, and for the deep link, the inviter's profile card appears and nothing is sent until **Send friend request** is tapped.

### Open rooms and room positions (2026-10-06)

- **Open rooms ("drop in").** `socialRoomAction` takes an optional `open: boolean`, accepted only with `create` and the new `open {roomId, open}` action (host only); any other action carrying `open` is `invalid-argument`, and older clients that leave it out keep working. Rooms store `open` (server-written, `false` by default). Opening needs the host's `sharingSettings.activity == "friends"` and invisible mode off (`failed-precondition` otherwise). While open, the server keeps `openRooms/{hostUid}` = `{schemaVersion: 1, roomId, hostUid, title, memberCount (joined), maxMembers, generation (the host's sharing generation), updatedAt, leaseExpiresAt}` in step with create/invite/join/leave/kick/heartbeat. It is deleted when the room closes or expires, when the host turns it off, on a host hand-off (the new host's room is `open: false`) and on **any** `socialUpdateSharing` by the host, which also sets the room's `open` to false. The app's incognito/invisible/hidden-title fence goes through that callable and leaves the room too. One card per host.
- **Drop-in join.** `join {roomId}` from someone who is not a participant succeeds only when the room is `open`, not closed and leased; the actor is an accepted friend of the host (no block either way) and neither blocks nor is blocked by **any** participant; the room has fewer than `maxMembers` participants; `openRooms/{host}` names this room at the host's current generation; and the host still shares activity with friends and is visible. Refusals are `permission-denied` "Room unavailable." whatever the reason (blocks can't be probed), except a full room (`resource-exhausted`) and a closed or expired one (`not-found`). The joiner becomes a `joined` participant at once (room event `joined`, `roomInvites` entry `active`).
- **Room positions.** New action `position {roomId, position: {chapterKey, pageIndex} | null}`: exactly those two keys (`chapterKey` a 64-hex key, `pageIndex` 0-1999), or `null` to clear. Joined participants only (the host's friendship is checked like for every room action); the room must be `active` and leased for a non-null place. At most one non-null update per `ROOM_POSITION_GAP` (3 s, `resource-exhausted` otherwise; clearing is never limited) and `ROOM_POSITIONS_PER_DAY` (6,000) per user, counted under its own quota key `roomPosition` (plus the 8,000 daily total). Stored as `rooms/{id}.members.{uid}.page = {chapterKey, pageIndex, at}` (server ms); `updatedAt`, `position`, `sequence` and `roomInvites` are untouched. Result `{roomId, room: {hostUid, state}}`. Leaving or being removed drops the member and the page with it.
- **Rules.** `rooms` accept the optional `open` bool (server-written; host position updates may still change only `position/sequence/writerSessionId/updatedAt`). `openRooms/{uid}`: the owner, or `shares(uid, 'activity')` with the host visible and either no card (an authorized "none") or `generation == sharing.generation` and `leaseExpiresAt > request.time`. Never client-writable. The card carries no content key, members, chat or position.
- **Privacy.** Everyone in a room sees which page each member is on in the room's title. The app shares it only while reading the room's title in the same edition, clears it on any other title, and stops when incognito, hidden titles or invisible mode end the room. A drop-in card tells a host's friends that the host is in an open room, its title and how many people are in it: the host's shared activity plus a count.

- **Challenges** (UTC calendar month, the same for everyone): `CHALLENGE_ROTATION[month - 1]` in `domain.ts` names three of `CHALLENGES` (`chapters_100`, `chapters_200`, `days_15`, `days_20`, `together_5`, `together_10`, `streak_7`, `streak_14`, `binge_15`, `xp_2000`; each has `{field, min}`). October: `chapters_100`, `days_20`, `together_10`.
- **Counters** inside `awardXp` (no extra reads): `xp/{uid}.month = {id: "yyyy-mm", chapters, days, together, streak, bestDay, xp}`, started fresh when `id` differs from the current UTC month (also for older docs without it). `streak` = longest XP streak reached this month (a streak begun last month counts), `bestDay` = most chapters in one UTC day this month, `xp` = reading XP this month (challenge XP excluded).
- **Completion**: when a counter reaches `min`, `+CHALLENGE_XP` (100) once, outside the daily cap, `today` and `weekXp`; stamped in `xp/{uid}.challenges = {"yyyy-mm": [ids]}` (kept for good). - **Mirrors**: the app's `XpRules` and web `logic.ts` copy these numbers; `XP rules table` (backend test), `XpRulesTest` (app) and `logic.test.mjs` (web) assert the same literal list, so any drift fails a test.

### Invisible hides everything (2026-10-14)

Berti's decision: invisible mode hides everything from friends, not only presence. `socialGetFriend` reports every visibility category as `private` while the owner is invisible; `socialPublishActivity` refuses a new activity while invisible (clearing still works); the rules add `invisible != true` to `projection()` (shared library, favorites, feed, daily stats) and to `activities`, and `storage.rules` hides cover thumbnails. Going invisible already bumped the generation (hiding older projections); this also covers anything republished while invisible. Reviews, XP, presence, last seen, open rooms and the ranking were already hidden.

### Ranking boards off the chapter's transaction (2026-10-14)

`socialRecordChapter` no longer touches `leaderboards/*` inside its transaction (Firestore's server SDK locks every document a transaction reads, so every ranked chapter used to contend on the same two documents). After the chapter commits, plain reads decide whether the reader is on the day's or the all-time board or would enter it (`boardWants`: listed already, room left, or a score beating the last entry; a newcomer loses ties), and only then a small transaction rechecks consent (`rankedGlobally`, matching generation) and updates those boards. A failed board update is logged and never fails the chapter; the next counted chapter places the reader again. The board contents and order are unchanged.

### Account deletion and rooms (2026-10-14)

Account deletion leaves each room first, through the same logic as `leave` (`SocialService.departRoom`, without the friendship checks, since the account's edges may already be going): a member is removed, a host hands over to the longest-present member, and a room with fewer than two people left ends. Only rooms that ended are removed entirely (room, lease, chat, every participant's index entry); a room others are still in carries on, and the deleted user's old chat lines stay until the room closes, like group chats.
